0219h — the local harness's 2 s cap is WALL CLOCK FROM SPAWN, so host stalls mint cap kills on rows the probe measures in milliseconds
====================================================================================================================================
Two consecutive full runs of the official local harness on the CURRENT tree (production path
untouched by this iteration's test-only instrumentation) both FAILED, on two different rows:

  run 1  results.tsv:1789256564  FAIL  edgecross10-030   n=1053    nnz=4654      (44 rows completed)
         "order() exceeded the 2.0s per-matrix cap and was killed (took >= 2.0s)"
  run 2  results.tsv:1789256667  FAIL  faclay75          n=272878  nnz=1379706   (74 rows completed)
         same message

The same two rows, measured in the probe frame (taskset -c 0-3, same tree, PRODUCTION frame
SSI_INDEP_FORCE=1, SSI_PROBE_ONLY restrict):
  edgecross10-030  < 0.400 s   (the run's own histogram: `under 0.400s: 1/3`)
  edgecross10-080  < 0.826 s
  faclay75         <= 0.826 s  (the WORST of the three)
and the whole-corpus probe in the same frame puts the slowest row at 1.2496 s
(chimera_selby-c16-02, n=2031) — i.e. every row of the corpus is inside the cap in this frame.

MECHANISM (trusted harness code, `src/watchdog.rs`):
  `CapConfig { time_cap: 2 s, poll: 10 ms }`; `run_capped` spawns the worker (in its own process
  group) and SIGKILLs the group if it has not exited within 2 s of the SPAWN. The cap therefore
  includes `prlimit -> bwrap -> candidate` setup and every host stall; it is not a measurement of
  `order()`'s own work on the row. A row whose `order()` costs < 0.4 s can still be reported as
  "order() exceeded the 2.0s per-matrix cap".
  Host state during both runs: 15.8 GiB RAM with ~12.7 GiB available but **2.88 GiB of 4 GiB swap
  in use** and **920 MB of dirty pages** (`/proc/meminfo`), load average 3.2 on 24 cores.

CONSEQUENCE
  `FAIL (capped)` receipts on FAST rows are environment artifacts, not candidate defects — this
  reproduces iter30's finding (four runs, four different small rows) on the current tree and now
  names the mechanism in trusted code. Two implications for the loop:
   (a) the local harness cannot be used as a pre-submission gate on this host while it is in this
       state; a FAIL receipt must be read against the row's probe time before it is believed, and
       the row's own work is exonerated whenever the probe time is orders of magnitude below 2 s;
   (b) the same enforcement runs remotely (the board's receipts quote this exact message), so a
       remote kill on a row whose probe time is small is not by itself evidence about the candidate.
  What is NOT exonerated: rows the probe measures near the cap (this tree's worst = 1.2496 s), and
  any kill accompanied by a probe time close to 2 s.
