iter69 — the graded frame's *system-time* axis, and a bit-exact cap-margin device
================================================================================

Frame: one `target/release/ssi-candidate-worker` process per dev matrix under
`taskset -c 0-3`, timed with `/usr/bin/time -f "%e\t%U\t%S\t%R\t%M"` (wall, user,
sys, minor faults, maxRSS-kB).  This is the frame the 2 s cap and the 4 GiB
`RLIMIT_AS` are actually charged in (src/watchdog.rs, src/sandbox.rs), and this
iteration is the first time the worker's *user/sys split* and *page-fault* profile
have been measured at all.

2. The mechanism: the mutable n*w fill-graph bitset is rebuilt per block entry
-----------------------------------------------------------------------------
`rgreedy::Game::assemble` copies the pristine bitset into a fresh
`n*ceil(n/64)`-word buffer (`adj: adj0[..n*w].to_vec()`); for `nd_netgen`
that is 33 155 * 519 = 17.2 M words = **137 MB per game**, and the class block
is entered many times per row.  glibc serves a block that large through mmap /
munmap (or a heap trim), so every game re-faults its pages from scratch:
346 910 minor faults ≈ 1.4 GB of first-touch traffic.

Upper bound, measured with the allocator's own knobs (same binary, same
patterns, 3 passes each, `0269-fault-ab-crown.txt`):

    nd_netgen  base 0.99/1.00 s, sys 0.34-0.36, 346-347 k faults
               MALLOC_MMAP_THRESHOLD_=1e9 MALLOC_TRIM_THRESHOLD_=-1
               0.73-0.74 s, sys 0.09-0.10, 86-87 k faults     (-0.26 s)
    every other crown row moves by 0.00-0.06 s; no row regresses.

Note `iter68`'s kill ("the 2^k*w scratch is NOT the exchange's DP wall", code
comment in window_dp.rs) is consistent: that arm routed k<=4 *component* calls
off the tight union path.  This is a different buffer — the per-game `n*w`
bitset, not the per-component `2^k*w` one.

3. The device: recycle one bitset buffer per thread (bit-exact)
--------------------------------------------------------------
`rgreedy.rs`: thread-local `ADJ_POOL` (one `Vec<u64>` per thread, <= 20 M words),
`assemble` takes it (`resize` + `copy_from_slice`, i.e. every word is written
before any read), `impl Drop for Game<'_>` returns it.  No algorithm changes.

Measured:
* `0269-pool300-permutation-identity.tsv` — pre/post workers run on all 300 dev
  patterns, output permutations md5'd: **300 SAME / 0 DIFF** (bit-exact).
* crown rows, 1 pass: nd_netgen 0.99 -> 0.73 s (faults 346 569 -> 111 233),
  dt3 1.05 -> 1.02, lee4_09 1.12 -> 1.09, methanol400 1.11 -> 1.09,
  procurement1large 1.03 -> 1.02, c16-01 0.78 -> 0.77, mpbp_48 0.98 -> 0.97;
  no crown row slower.
* corpus pass (`pool-300.tsv`): minor faults **5.50 M -> 3.87 M (-30 %)**,
  sys 6.3 -> 4.7 s.  Single-pass wall totals (140.0 -> 134.1 s) are *not*
  usable evidence: individual row walls move by up to +-1.4 s run-to-run on
  this shared host (rows with bit-identical output "regress" by 0.8-1.4 s).
  The fault counts are deterministic; the wall deltas above are the 3-pass ones.
* official local sandboxed harness, 300/300 OK, no FAIL:
  **0.790243 / 0.923082** (buckets 0.887274 / 0.837472 / 0.682047) —
  identical to the same tree without the device (`results.tsv:1789310265`),
  as a bit-exact device must be (results.tsv:1789312709, score.json).

4. The local harness's 2 s cap is not a faithful proxy on a loaded host
----------------------------------------------------------------------
Five local harness runs this iteration (four with the pooled tree, one with the
pre-change control staged):

    1789312201 FAIL faclay35                 standalone wall 0.51 s (3 reps)
    1789312252 FAIL pooling_sppc1pq          standalone wall 0.40 s (3 reps)
    1789312386 FAIL crudeoil_pooling_dt3     standalone wall 1.02 s (CONTROL tree)
    1789313115 FAIL st_bsj2                  n = 13, nnz = 40

The control tree (no device) is killed too, so the kills are not the device's.
`st_bsj2` (13 variables, 40 nonzeros) cannot take 2 s of `order()` on any host:
the harness's child is being starved (host load 5.1, 2.8 GB of 4 GB swap in use,
`/proc/pressure/memory` full avg10 3.8 %), and the parent charges that starvation
to the per-matrix cap.  Consequence for this lane's model: local "cap kills" and
possibly some remote `failed` receipts are *artifact-prone on both ends*, so
every cap conclusion needs the same-day paired evidence it already uses.

5. What it is worth
-------------------
Value: exactly zero (bit-exact; the official run reproduces 0.790243/0.923082).
Cap: the fault wall is host-independent and is the *second* wall of the heavy
class (0.26 s on the widest row, 0.03-0.05 s on the charge-limited top rows).
`nd_netgen` moves from 0.99 to 0.73 s at the 3 GiB rung, i.e. out of the band
where the hidden slowdown (f in (1.82, 1.98]) can push a row past 2 s.
