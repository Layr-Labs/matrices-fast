Why this exists
---------------
Two claims in this lane's record contradicted each other and neither matched a primary
artifact: (a) the board said "frontier unchanged at 0.840782" while iter73's own source
comment said bat `bbf5849` was promoted at 0.840623; (b) the local harness killed the
20-sweep tree on `arki0013` with "took >= 3.2s", while a direct run of that same binary on
`.scratch/widthcensus/pats/arki0013.pat` finished in 0.66 s. Chasing (b) found the bug.

1. The defect (source-level, verified)
--------------------------------------
The per-row "graded frame" that this lane has used since iter65 — `.scratch/widthcensus/`
`extract.py` -> `pats/<row>.pat` -> production `ssi-candidate-worker <pat> <out>` under
`taskset` — is **not** the frame the graded harness charges the 2 s cap in.

    extract.py writes the RAW corpus arrays: n | len(indptr) | indptr | len(indices) | indices
    ssi-scoring/src/loader.rs:46   pattern_from_jsonl_line() DROPS THE DIAGONAL (i == j) and
                                   rebuilds through Pattern::from_adjacency; its own unit test
                                   pins it (`jsonl_line_parses_and_drops_diagonal`, :140-155:
                                   "12 raw entries - 4 diagonal = 8 off-diagonal").
    src/main.rs:269                the parent stages EXACTLY that loaded Pattern for the worker
                                   (`ssi_worker_protocol::write_pattern(pat_file.path(), pat)`).
    ssi-worker-protocol/src/lib.rs:29  read_pattern() is a round-trip reader; it strips nothing.

So the harness's worker input = raw corpus MINUS the diagonal; the lane's `.pat` files = raw
corpus INCLUDING it. The defect is exactly `n` entries per row, and it is visible in the
grader-facing numbers themselves:

    arki0013        raw 205081 -> harness nnz 160172  (= 205081 - 44909); the cap-kill message
                    prints "n=44909, nnz=160172, nnz/n~3"
    crudeoil_lee4_09 raw 117696 -> harness nnz 101792 (= 117696 - 15904); the harness table
                    prints "crudeoil_lee4_09 15904 101792"
    strip_diag.py (new, .scratch/iter73/) reproduces both exactly: 160172 / 101792.

It is a BEHAVIOURAL difference, not a relabelling: same binary (`worker-s12-ctl`), same row:

    arki0013         .pat(with diagonal) 0.65 s  perm md5 20cf0a38a1f34b0f
                     contract(no diagonal) 1.22 s perm md5 61e9069becff9439
    crudeoil_lee4_09  .pat 1.01 s perm md5 afb48d7350b2bb47
                     contract 1.20 s perm md5 d4a9b6c49a4c82e9

Different wall, different output permutation. Every `.pat`-frame wall in iter65-iter73
(the ranked-list census, the crown rows, the 1-core frame, the ledger ladder, the
sys/fault census, the iter72 A/B sweep) measured a different graph than the graded one.

Row-level size of the error (old .pat frame -> true frame, production worker, 4-core):
`gams05` 0.48 -> 0.89 (+85 %), `arki0013` 0.65 -> 1.21 (+86 %), `crudeoil_lee4_10`
0.75 -> 1.21 (+61 %), `chimera_selby-c16-01` 0.96 -> 1.10, `mpbp_48` 0.96 -> 1.07,
