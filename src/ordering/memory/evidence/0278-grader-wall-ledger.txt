3. WHY A TREE OF THIS PROFILE IS KILLED, NOT "UNLUCKILY KILLED"
---------------------------------------------------------------
From this tree's own probe-frame per-row wall (evidence/0277-probe-dense-on.log, 300 rows,
corpus order = corpus/dev/patterns.jsonl order, one call per row, 153.8 s total):

  >= 1.30 s :   4 rows ( 1.3 %)   3.4 % of the corpus wall
  >= 1.25 s :   5 rows ( 1.7 %)   4.3 %
  >= 1.10 s :  23 rows ( 7.7 %)  17.9 %
  >= 1.00 s :  34 rows (11.3 %)  25.3 %
  >= 0.90 s :  44 rows (14.7 %)  31.4 %

A row that reaches the hidden cap needs hidden >= 2.0 s; with the lane's own bracket
f in (1.53, 1.5625] that is a local row >= 1.28-1.31 s (4 rows), and if the hidden corpus's
rows are ~1.45x heavier per unit (see 4. below) the killable class is the >= 1.10 s class
(23 rows, 17.9 % of the wall). The observed kill window — 83-117 s for every tree that is
not pathological, i.e. 14-19 % of the corpus wall — is where the FIRST such row lands in a
shuffled corpus; the one 5.5 s kill shows the same rule with a much slower tree in front of
it. Reading: for a tree of this profile the kill is the *expected* outcome, not a per-bat
accident — the hot class straddles the cap, so ~every submission dies and the few that
complete are draws from the same distribution.

4. THE CORPUS-LEVEL CALIBRATION (already in the record, restated with its receipts)
-----------------------------------------------------------------------------------
iter70's measurement: our own sandboxed run of the promoted tree takes 281.0 s on the dev
corpus (2 calls per row, same shape as the grader), while the grader's run of the same tree
took 633-634 s on the hidden corpus => corpus-level ratio 2.25-2.26, against the max-row
ratio 1.53-1.56. The hidden corpus therefore carries ~1.45x more work per unit of host speed
than dev, and our dev-frame "safe line" (max row 1.28 s) is optimistic: the hidden frame's
own safe line for a dev row is ~0.88 s.
