3. THE BASIN EFFECT (the new device axis)
-----------------------------------------
The chain's acceptance is greedy: it moves the incumbent into a basin that the
remaining monotone stages then refine. Suppressing it is *worse* on 41 rows but
*strictly better* on 17, and the best of those are large: `crudeoil_lee4_06`
32 348 553 -> 31 062 855 flops (-3.98 %, ~4.4 s of pipeline wall avoided),
`waterund14` -2.35 %, `chimera_mgw-c8-439-onc8-001` -2.32 %,
`edgecross10-080` -1.68 %, `crudeoil_lee1_07` -1.55 %, `gasprod_sarawak16`
-1.34 %. Taking the *minimum of the two lineages' flops per row* is therefore
one-sided by construction: it can only improve, and it is a deterministic
function of the pattern (fixed shape gate, exact-flops comparison, ties keep the
shipped lineage).

Implemented in `order()`: gate `n <= 600 && nnz <= 5 000`; both lineages run
concurrently via `std::thread::scope` on the same `&Pattern`, each with its own
thread-local `CHAIN_LINEAGE` flag that `leader_order`'s chain reads. Rows
outside the band take the byte-identical pre-fork path.

-------------------------------------------------------------------------

written permutation: [.scratch/iter79/ab-lt1k.tsv]
  no fork     41.8 s   max row 0.81 s (`multiplants_stg1b`)
  n < 1000    48.5 s   max forked row 1.21 s          -> +0.65 s on ONE row
  n <= 600    43.3 s   max forked row 0.72 s          <- shipped gate
The fork's cost tracks the row's own cost (median +0.01 s), and inside `lt_1k`
that cost is monotone in `n` (class max 0.52 s at n<=400, 0.59 s at n<=600,
0.81 s at n<1000), so the gate bounds the forked critical path at 0.72 s while
keeping 3 of the 5 rows whose permutation the fork actually improves. The two
dropped rows (`multiplants_mtg1b`, `sonet24v5`) are worth 0.11 bips combined and
cost 1.05-1.21 s forked.
