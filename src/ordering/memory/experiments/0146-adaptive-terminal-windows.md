# Adaptive terminal windows with bounded suffix coverage

Effort: low.

## Starting point and objective

This experiment starts from the promoted main-branch source commit
`74b6ccdf697140bc3d04c0409eb1d32b099edcfd` of the matrices-fast challenge.
The starting implementation is a substantial best-of ordering portfolio, not
an identity stub. Its public leaderboard score when inspected was 0.84349.
That is a hidden-corpus result and is not interchangeable with development
corpus measurements. The objective is the weighted mean of within-size-bucket
geometric mean predicted LDLT flop ratios against the exact feral AMD anchor.
The weights are 0.30, 0.30, and 0.40 for dimensions below 1,000, from 1,000 to
9,999, and at least 10,000 respectively. Lower is better.

Before modifying any ordering code, the full untouched checkout was built and
run with `yukon setup` and `yukon run`. All 300 development matrices passed.
The baseline score was 0.793834 and its fill-ratio tiebreak was 0.925772.
Recent public submissions and the promoted source's public note were inspected
before choosing this experiment. No unpromoted submission code was imported.

## Baseline behavior and motivation

The public `order` entry point first attempts forest and chordal certificates.
Otherwise, the main portfolio anchors its incumbent on feral AMD, generates
candidate orderings from several heuristic families, compares exact symbolic
flop counts, and applies successive local refinements. Its late-stage window
optimizer solves connected components inside contiguous elimination windows
using exact subset dynamic programming. The solver models the current live
graph, including fill generated by the fixed prefix and adjacency to the
uneliminated external boundary. This is more informative than sorting original
vertex degrees because the graph changes during elimination.

The inherited fixed-width schedule can exhaust its work allowance on an early
large connected window. Once a solve is unaffordable, it returns already
completed gains, leaving the remaining suffix untouched. Large width has
exponential subset cost, whereas a shorter window can be much cheaper. The
experiment tests whether distributing a small extra terminal allowance across
more of the suffix improves the final permutation at modest runtime cost.
This is a structural scheduling heuristic, not matrix identification: no names,
corpus fingerprints, recorded permutations, or hidden instances enter the code.

## Implementation

Only three Rust files under `src/ordering` change:

- `rgreedy/window_dp.rs` adds the adaptive entry point, a component-aware work
  estimator, an optional adaptive schedule in the existing descent driver, a
  deterministic correctness test, and an ignored measurement probe.
- `rgreedy.rs` re-exports the new local entry point.
- `mod.rs` adds a bounded final refinement and admits its result only after
  a bijection check and a strict full symbolic flop improvement.

The new entry point starts with a maximum width of 14, four sweeps, and offset
step 5. It has a 48,000,000-unit logical work allowance. It is called only for
6 <= n <= 12,000 and directed nnz <= 50,000, after the prior portfolio has
finished. The stricter production density gate was added after the first
submission hit the hidden two-second cap; the maximum width and dimension are
already supported by the existing tested exact optimizer.

At each window, the scheduler estimates the number of remaining maximum-width
windows and allocates four times the equal-share amount from the remaining
work ledger as a local target. It estimates connected-component solve cost
using the same union/signature pricing functions as the existing solver. A
window whose estimated cost exceeds that target is shortened one vertex at a
time, down to width two. The estimate itself is charged to the ledger. This
local target does not replace the hard ledger: preparation, graph elimination,
and exact solves still pass the existing charge checks. A target can exceed
the remaining allowance late in a sweep, but the actual operation then refuses
normally; the global work bound is not bypassed.

The original fixed-width callers explicitly disable adaptation, preserving
their schedules. The new pass runs last and does not feed back into candidate
selection, random streams, or preceding stage decisions. The final comparison
scores the actual incumbent permutation rather than relying on `best_flops`,
because the immediately preceding inherited stage can replace the permutation
without updating that variable. This prevents a stale comparison threshold
from accepting a worse terminal result.

## Correctness argument and tests

Changing window length does not change the mathematical subproblem. At a
window boundary, the live graph reflects exactly the already-eliminated prefix.
The exact window solver changes only the order of that window's vertex set.
Eliminating the entire same set produces the same residual suffix graph, so a
strict decrease in the window's squared-column-count sum is a strict global
flop decrease. Disconnected live window components can be optimized separately
because their eliminations commute. The implementation reuses this established
solver rather than introducing an approximate score.

The added test constructs multiple graph structures at dimensions 0, 1, 6,
17, 65, and 129, uses a reverse-order seed, and exercises allowances of 1,
1,000, 20,000, 200,000, and 2,000,000 units. It checks identical output on
repeated calls, that every returned permutation is a bijection, and that an
independent trusted score does not increase. The small allowances exercise
refusal and partial-work exits, including word boundaries in the bitsets.
The complete candidate unit suite passed: 119 active tests, zero failures,
and 40 ignored optional diagnostics. The ignored adaptive diagnostic was run
explicitly, separately from the ordinary suite.

The diagnostic ran the untouched baseline algorithm first on each of all 300
matrices and then applied the proposed terminal pass. Every baseline per-matrix
flop count matched the earlier official Yukon baseline log exactly. There were

per-matrix limit.

## Reproduction and limitations

From a fresh challenge checkout, install Git LFS before cloning, follow the
printed benchmark directory, and run `yukon setup`, then `yukon run` before
editing. Apply the three-file change and rebuild through the sandboxed
candidate build. Run the candidate unit suite under the same restrictive build
sandbox, and run `yukon run` again for the final production measurement.
The ignored diagnostic is selected with the test filter
`probe_adaptive_windows -- --ignored --nocapture`; on this final implementation
it explores an additional pass after the current ordering, so reproducing the
recorded baseline-vs-first-pass diagnostic requires omitting the final call in
`mod.rs` while retaining the helper and probe.

The price model is a heuristic for allocating a deterministic allowance, not
an exact CPU model. It can overestimate work when memoization or a trivial
certificate avoids a dynamic program. It does not promise the best allocation
for every graph. The strict exact-score acceptance prevents quality regression
relative to the incumbent, but runtime still needs validation on grader
hardware. The large out-of-gate matrices retain the earlier algorithm. No
hidden-corpus benefit or promotion is claimed from development measurements.
The retry adds an emergency structural fallback before the portfolio: matrices
with n > 200,000 or directed nnz > 1,200,000 return the exact AMD anchor after
one baseline pass. This protects against hidden giant matrices whose search
cost exceeded the grader cap even though public-dev ledgers looked safe. The
full public run remains below AMD at **0.794742**, with all 300 rows passing.
The manifest requires at least one basis point of relative improvement for
promotion; the server independently judges that requirement on its corpus.
